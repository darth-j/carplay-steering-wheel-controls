# Build, integration and deployment

## English

### What can be deployed from this repository?

This repository provides a portable logic library and a [reference head-unit adapter build kit with GEM installer templates](adapter/GEM-INSTALL.md). The kit builds target classes locally from the operator's original dependencies, then generates a full GEM tree. No proprietary SDK, firmware dependency JAR, complete stock class or precompiled OEM-derived payload is distributed. The portable `build.sh` JAR alone is not the GEM payload. Other targets still need their own reviewed adapter and installer.

All project-authored code here, including build scripts and tests, was generated by AI. OEM patch context retains its original ownership; see [adapter/ADAPTER-NOTICE.md](adapter/ADAPTER-NOTICE.md). **Flashing or modifying firmware is risky and can brick a head unit or interrupt vehicle functions. Test cautiously.** Back up the original software, keep an independent recovery path, maintain stable power and only perform device testing while parked.

### 1. Test the portable logic

Install JDK 17 or later, then run from the repository directory:

```sh
sh test.sh
```

The tests use fake ports, synthetic events and a virtual clock. A pass confirms portable logic behavior, not hardware compatibility or firmware safety.

### 2. Build the library JAR

```sh
sh build.sh
```

Output:

```text
dist/carplay-steering-wheel-controls.jar
```

The artifact contains the two production classes and their nested types, plus GPLv3 and attribution files under `META-INF`. It excludes the test class, private fixtures, firmware and credentials. `dist/` is excluded from Git by the publication allow-list.

This default artifact targets Java 8 bytecode, class-file major version 52. **It is not suitable for an older embedded JVM that rejects that version.** The Java runtime on the target determines the required compiler, source/target flags, boot dependencies and verification procedure. Those compiler dependencies must be obtained locally; do not add proprietary SDK or firmware files to this repository.

### 3. Implement the device adapter

See [INTEGRATION.md](INTEGRATION.md). The adapter must:

1. Map verified physical inputs to the four logical keys and distinguish steering-wheel events from console events.
2. Feed real connection, page, playback and call state. Subscribe to the source call-state stream; an unused callback is not a subscription.
3. Implement every `Port` method using the target's existing services, including paired media events and a complete Siri press/long/release sequence.
4. Provide a monotonic `Clock` and a nonblocking `Scheduler`.
5. Apply the playback guard at the outbound native transport boundary, not just commands from this library.
6. Preserve native input handling whenever `onKey` returns false, and retain the target's input/power restrictions.

Bundle the compiled core with that adapter using the target's documented packaging method. The deployment payload is **the compatible adapter plus this library**, not the default JAR on its own. The portable core has no target IDs; the reference adapter publishes reviewed, non-unique technical mappings and generic class fingerprints, but no vehicle identity, private startup snapshot or diagnostic endpoint. Generic reference-model and software-version information is listed in [COMPATIBILITY.md](COMPATIBILITY.md).

### 4. Verify on the target before modifying startup

Record the target runtime and active software locally. Verify the candidate's class-file versions, dependency resolution, class loading, initialization and relevant callbacks in an isolated test process where the platform supports one. Do not start a second production UI or replace a running UI merely to test whether a class loads.

Do not enable permanent loading until the adapter has a known-good backup, an independent recovery method and a successful temporary device test. Do not assume a syntactically valid shell script is compatible with the target's older shell and utilities.

### 5. Transfer and verify the payload

The following is a **transport example only**, not an installer. Replace `USER`, `HOST` and the staging path with locally configured values. No defaults or credentials are supplied by this project. Use a staging path known to be writable on the target; do not guess a firmware installation directory.

If a compatible SCP/SFTP implementation exists, it may be used. Otherwise a shell stream can transfer a file:

```sh
ssh USER@HOST 'cat > staging/controls.jar' < dist/carplay-steering-wheel-controls.jar
```

Read the staged file back to the development machine and compare it there:

```sh
ssh USER@HOST 'cat staging/controls.jar' > returned.jar
cmp dist/carplay-steering-wheel-controls.jar returned.jar
```

These commands transfer the library only. Transfer the separately built adapter and any manifest using the adapter's instructions. Do not overwrite the head unit's production file at this stage. A shell stream avoids assuming that SCP, SFTP or checksum tools are installed on an embedded target.

### 6. Install using the adapter's reviewed procedure

There is intentionally no generic flashing command. A valid target-specific procedure must:

- Identify the exact expected current software and refuse mismatches.
- Back up the known-good adapter and startup entry without overwriting an existing verified recovery copy.
- Verify the candidate and backup through supported checksums or read-back comparison.
- Stage final replacements on the same filesystem and publish by atomic rename where supported.
- Restore read-only mounts and flush writes if required by that platform.
- Keep a disable/bypass path and a working management/recovery channel.
- Separate file deployment from restart authorization. Never embed an unconditional reboot after a failed installation command.

**Do not paste a startup line, mount command or binary offset from another head unit.** This repository does not establish the correct installation path, mount layout, launch arguments or recovery procedure for a particular device.

### 7. Validate a temporary load

After an explicitly coordinated restart, check that the expected payload really loaded, that the UI is responsive and that there are no load/verification errors. Then test:

- Native passthrough on other pages and on console controls.
- Next/previous track, explicit pause/play and normal audio focus behavior.
- Siri recognition and execution, not merely showing the listening UI.
- Connection while already playing versus connection while paused; repeat after disconnect/reconnect.
- Incoming call answer, active-call hangup and rejection without accidentally answering.
- No media action during calls, no stuck keys and no stale delayed release after disconnect.

Call-waiting, multiple phones, different applications and firmware variants require additional adapter-level validation. Do not mark an untested rejection delay or compatibility combination as verified.

### 8. Permanent enablement and rollback

Permanent loading is a **target-adapter feature**, not a feature of `build.sh`. Only enable it through the adapter's verified persistent loader after temporary testing. Confirm that required dependencies remain available without the development card or staging files.

If the UI fails, input becomes stuck or call behavior is wrong, stop repeated installation attempts. Use the independent recovery channel to disable the adapter or restore the verified known-good payload/startup entry. Recheck the restored file, then coordinate a restart. If the restoration cannot be verified, preserve the current state and do not blindly flash another package.

The order is: **build → adapt → stage → verify → temporary load → hardware tests → optional permanent enablement**. The portable build/test path is separate from the strict-profile reference GEM builder. Follow the reference GEM guide for that target; it does not establish compatibility with other devices.

## 中文

### 当前仓库能直接部署到车机吗？

不能直接复制独立逻辑库 JAR 就完成安装。仓库现已提供 [参考适配构建工具和 GEM 安装模板](adapter/GEM-INSTALL.md)，使用操作者自己的原始依赖生成完整 GEM 包；不公开厂商 SDK、原厂依赖 JAR、完整原厂类或预编译的原厂衍生产物。其他目标仍需单独适配，范围见 [COMPATIBILITY.md](COMPATIBILITY.md)。

本仓库项目原创代码（包括构建脚本和测试）全部由 AI 生成；原厂补丁上下文保留原有权利归属。**刷机或修改固件有风险，可能导致车机无法启动或影响车辆功能，测试需谨慎。** 请备份原始软件、保留独立恢复通道、保持供电稳定，并仅在车辆停稳时进行设备测试。

### 1. 测试和构建

安装 JDK 17 或更新版本，在仓库目录运行：

```sh
sh test.sh
sh build.sh
```

生成 `dist/carplay-steering-wheel-controls.jar`。其中包含生产逻辑、嵌套类型及 `META-INF` 中的 GPLv3 许可和来源说明，不包含测试类、固件或私人数据，`dist/` 不提交到 Git。

**默认产物是 Java 8 字节码（major 52），不能直接放进不支持该版本的旧嵌入式 JVM。** 需要依据目标运行时选用兼容的编译器、目标版本和本地依赖，并在原运行时验证。不要把厂商 SDK 或固件依赖上传到公共仓库。

### 2. 接入目标设备

按 [INTEGRATION.md](INTEGRATION.md) 实现 `Port`、`Clock`、`Scheduler`，并接入真实的连接、页面、播放和电话状态。

必须核对物理按键来源、订阅实际电话回调、完成 Siri 的按下／长按／松开序列、非阻塞调度拒接释放，并在原生输出边界接入播放保护。未被逻辑消费的事件必须交回原厂。

最后按目标平台的方式把“核心库 + 设备适配器”一起打包。独立逻辑库构建成功不等于已有车机安装包；参考适配目标需运行专用 GEM 构建器并满足全部校验。

### 3. 暂存和校验

先核对当前软件和运行时，再在可行的独立测试进程里验证类加载、初始化和回调；不要为了测试类加载而误启动第二套生产界面。

前面的 SSH 示例仅用于传输，`USER`、`HOST` 和暂存路径都需要自行替换。先上传到确认可写的暂存位置，再读回到电脑用 `cmp` 比较，不要直接覆盖生产文件，也不要假定目标设备一定装有 SCP、SFTP 或校验工具。

### 4. 安装、重启和测试

安装必须使用目标适配器提供的流程：核对版本、保存旧程序及启动项、验证备份和候选、在同文件系统暂存后原子替换、恢复挂载状态、同步写入，并保留禁用和恢复入口。

**没有适配器和已验证路径时，不应照抄其他设备的挂载命令、启动行或二进制地址。** 文件部署与重启授权应分开；安装失败后不能无条件继续重启。

先进行临时加载，重启后确认新程序确实加载且界面正常，再验证原厂事件透传、四键音乐/Siri、连接前播放/暂停、电话接听/挂断/拒接、断连清理，以及中央控制台原有行为。不能只看“脚本执行完毕”就认定成功。

### 5. 永久生效和回退

永久加载由目标适配器负责，`build.sh` 不会修改任何启动项。临时测试通过后才可启用已验证的永久加载方式，并确认不依赖开发 SD 卡或 RAM 暂存文件。

出现界面卡住、按键卡住或电话行为异常时，先停止反复安装，通过独立恢复通道禁用适配器或恢复已校验的旧程序和启动项。恢复文件核对成功后再协调重启；恢复不能确认时不要继续盲刷。

整体顺序为：**构建 → 适配 → 暂存 → 校验 → 临时加载 → 实机测试 → 按需永久生效**。独立逻辑库与参考 GEM 构建路径分开；参考目标按 GEM 专用指南操作，其他设备不能照搬安装器。
